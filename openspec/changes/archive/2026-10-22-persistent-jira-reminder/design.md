# Design

## Context

См. `proposal.md`. Сейчас `send_message.py` за один запуск читает `.env`, `message.json` и `data/sent.json`, шлёт статичный текст и завершается. Образ уже запускает этот файл, Compose держит `restart: unless-stopped` и том `reminder-data` на `/app/data`. Ключ слота `YYYY-MM-DDTHH` и срок хранения записей 7 дней остаются. Требования — в `specs/reminder-schedule/spec.md` и `specs/jira-digest/spec.md`.

## Goals / Non-Goals

**Goals:**

- Один процесс `send_message.py` сам ждёт часы `SEND_HOURS` в `TZ` и догоняет неотправленные слоты только текущих суток.
- Один и тот же путь отправки для старта и для срабатывания cron: сводка Jira, затем Telegram, затем запись ключа.
- Jira Cloud через `requests`, без отдельной библиотеки. Карта пингов с диска, перечитывается на каждую отправку.

**Non-Goals:**

- Поминутный тикер, хранилище задач APScheduler, AsyncIOScheduler и APScheduler 4.x.
- Диалоговый бот, webhook, смена статуса Jira, комментарии, отдельное сообщение на каждую задачу.
- Догон вчерашних слотов и смена формата ключа.
- Jira Server/Data Center и Bearer PAT. Аутентификация — basic auth Jira Cloud.

## Decisions

### Постоянный процесс на BlockingScheduler 3.x

В `requirements.txt` фиксируется `apscheduler>=3.10.0,<4`. Верхняя граница нужна потому, что 4.x меняет API, а код синхронный.

`BlockingScheduler(timezone=tz)` блокирует главный поток. Задача одна: `CronTrigger(minute=0, hour="<часы через запятую>", timezone=tz)`, `max_instances=1`, `coalesce=True`, `misfire_grace_time=300`. Пять минут запаса закрывают задержку уже запущенного процесса около `:00`. Простой выключенного процесса это не догоняет — для него отдельный проход при старте.

`AsyncIOScheduler` не берём: пришлось бы заменить `requests` на асинхронный клиент. Интервал раз в минуту не берём: это тикер, его запрещает спецификация расписания.

Остановка: `SIGTERM` и `SIGINT` вызывают `scheduler.shutdown(wait=False)`. Контейнер Linux; локальный Ctrl+C на Windows приходит как `KeyboardInterrupt` из `start()`. `CMD` образа и имя файла не меняются.

### Один проход по должным слотам суток

И старт, и срабатывание cron вызывают одну функцию. Она берёт текущее время в `TZ` и для каждого часа из `SEND_HOURS`, который уже наступил сегодня (`hour <= now.hour`) и чьего ключа нет в `sent.json`, один раз собирает сводку и шлёт её. Часы идут по возрастанию.

Поэтому:

- старт в 20:30 отправляет пропущенный слот 19 и не трогает завтрашний;
- старт на следующий день не видит вчерашние ключи как должные;
- старт в 10:00 при первом часе 19 ничего не шлёт;
- срабатывание в 21:00 заново пытается неотправленные 19 и 20 этих суток, если они так и не записались.

Пока слот не в файле, повтор возможен. Записанный слот функция пропускает. Два входа не выполняются параллельно: проход при старте заканчивается до `scheduler.start()`, у задачи `max_instances=1`.

Внутри одной попытки слота — до трёх обращений к Jira и Telegram с паузой 30 секунд. Это не новое расписание, а повтор той же отправки. После третьей ошибки ключ не пишется, процесс остаётся жить. Если в `SEND_HOURS` только один час, следующая автоматическая попытка этого слота будет только при перезапуске в те же сутки.

### Сводка Jira

Настройки `JIRA_URL`, `JIRA_USER`, `JIRA_API_TOKEN`, `JIRA_BOARD_PROJECT_KEY` обязательны на старте, рядом с `BOT_TOKEN`, `CHAT_ID` и `TZ`. Пустое значение или `JIRA_URL` не на `https` завершает процесс до планировщика, чтобы токен не ушёл по голому HTTP. Ключ проекта принимается только если это буквы, цифры и `_` и он начинается с буквы: так значение из `.env` не разбивает JQL.

Запрос: `POST {JIRA_URL}/rest/api/3/search/jql` с basic auth. Тело: JQL из спецификации, `fields: ["summary", "assignee"]`, `maxResults: 50`, дальше `nextPageToken`, пока он есть и текст ещё помещается в лимит. Старый `POST /rest/api/3/search` на Jira Cloud снят, его не используем.

`assignee.displayName` сравнивается с ключом `users_map.json` как точная строка. Нет исполнителя — в строке «без исполнителя». Нет ключа в карте — имя без пинга. Ссылка: `{JIRA_URL}/browse/{KEY}`.

Текст слота:

```
{text из message.json}

PROJ-1: Название
Исполнитель: Иван Иванов @ivan
https://host/browse/PROJ-1
```

Пустая выборка: базовый текст и строка «Незакрытых задач нет.» Если `parse_mode` равен `HTML`, в название, имя и ключ подставляются с экранированием `&`, `<`, `>`. Пинг остаётся как в карте. При обрезке по лимиту Telegram 4096 заголовок сохраняется, в конце строка «… список обрезан, показаны не все задачи.»

`message.json` и `users_map.json` читаются внутри попытки, не на старте. Путь карты — `USERS_MAP_PATH`, по умолчанию файл рядом со скриптом. Ошибка файла или HTTP Jira — исключение попытки, без записи слота и без токена в логе. В лог попадают статус HTTP и ключ слота.

### Файлы окружения

Compose монтирует `./users_map.json:/app/users_map.json:ro` рядом с уже смонтированным `message.json`. В репозиторий кладётся `users_map.example.json`. Сам `users_map.json` добавляется в `.gitignore` и `.dockerignore`, как `message.json`: в образ он не копируется. `.env.example` получает четыре пустые переменные Jira. `README.md` описывает постоянный процесс, догон суток и обязательные файлы на сервере; внешний cron убирается из инструкции запуска.

Формат `data/sent.json` (`{"sent": ["YYYY-MM-DDTHH", ...]}`) и чистка старше 7 дней не меняются. Уже лежащие ключи остаются действительными.

## Risks / Trade-offs

- [Статус в JQL буквально `In Progress`] → Локализованное имя вроде «В работе» в сводку не попадёт. Это зафиксированный запрос, не настройка. Смена формулировки — правка спецификации.
- [Одинаковые `displayName` у разных людей] → Пинг получит первое совпадение по строке. В карте имена должны быть такими, как их показывает Jira, и уникальными.
- [Один час в `SEND_HOURS` и три неудачные попытки] → До следующего перезапуска в те же сутки слот сам не повторится. Пауза между попытками короткая специально, чтобы не устраивать тикер.
- [Догон нескольких часов подряд шлёт несколько сводок] → Так и задумано: ключ остаётся почасовым. Три пропущенных часа — три сообщения при старте.
- [`restart: unless-stopped` при падении на битом `.env`] → Docker будет поднимать контейнер снова. Это уже текущая политика. Ошибка настроек должна быть видна в логе с первой строки, без отправки.
- [Обрезка списка по 4096 символам] → Хвост задач в сообщение не входит, пометка об обрезке обязательна. Полный перечень в нескольких сообщениях не шлём: на слот положено одно сообщение.
- [Поиск Jira не консистентен сразу после правки задачи] → Для почасовой сводки это приемлемо. `reconcileIssues` не используем: бот сам задачи не меняет.

## Migration Plan

1. Убрать системный cron, который вызывает `send_message.py`, до выката нового образа. Иначе два планировщика спорят за один слот; первый успешный записывает ключ, второй пропускает отправку.
2. На сервере рядом с `message.json` положить `users_map.json`. В `.env` добавить четыре переменные Jira.
3. После публикации образа: `docker compose pull` и `docker compose up -d`. Том `reminder-data` не удалять.
4. Откат на старый образ возвращает процесс, который завершается после одной попытки. С `restart: unless-stopped` контейнер начнёт сразу перезапускаться. Откат имеет смысл только вместе с возвратом внешнего cron и пониманием, что текст снова будет только из `message.json`. Предпочтительный откат — предыдущий sha-тег образа из GHCR, не удаление тома.

## Open Questions

Нет. Статус `In Progress`, basic auth Jira Cloud и догон каждого должного часа текущих суток зафиксированы в спецификациях и выше.
