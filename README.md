# telegram-reminder

Постоянный контейнер раз в заданные часы отправляет в группу Telegram одно сводное сообщение: заголовок из `message.json` и список задач Jira в статусе In Progress. Расписание живёт внутри процесса. Системный cron для отправки не используется.

Образ собирает GitHub Actions при пуше в `main` и публикует в GitHub Container Registry:

`ghcr.io/rdog49/reminder_telegram_bot:latest`

Сборка идёт под `linux/amd64`. На сервере образ не собирается: `docker-compose.yml` скачивает его и запускает. Токены, id группы и тексты в образ не входят.

Процесс после старта не завершается. В каждую минуту 00 часов из `SEND_HOURS` (часовой пояс `TZ`) уходит одно сообщение. Если контейнер в этот час был выключен, но календарные сутки в `TZ` ещё те же и слот не отправлен, сообщение уходит при старте. На следующие сутки пропущенный слот не догоняется: бот ждёт ближайший час из `SEND_HOURS`. Успешный слот записывается как `YYYY-MM-DDTHH` в том `reminder-data` и второй раз в этот час не отправляется.

## 1. Что делать с прошлым ботом на сервере

Сделайте это до выката новой версии. Иначе старый cron и новый процесс отправят одно и то же окно дважды: первый успешный запишет слот, второй его пропустит.

### Удалить задачу из crontab

Откройте crontab того пользователя, под которым раньше запускался скрипт. Если задача была у root:

```bash
sudo crontab -e
```

Если задача была у обычного пользователя, без `sudo`:

```bash
crontab -e
```

Удалите строку, которая вызывает `send_message.py`, `python` этого бота или `docker`/`docker compose` по расписанию. Остальные задания не трогайте. Сохраните файл и выйдите из редактора.

Проверьте, что строки больше нет:

```bash
sudo crontab -l
crontab -l
```

В выводе не должно остаться команды этого бота. Пустой crontab отвечает `no crontab for ...` — это нормально.

Расписание теперь внутри контейнера. Новую задачу в cron добавлять не нужно.

### Остановить старый контейнер

Перейдите в каталог, где уже лежит старый `docker-compose.yml`. Обычно это `/opt/telegram-reminder`:

```bash
cd /opt/telegram-reminder
sudo docker compose down
```

Команда останавливает и убирает контейнер `telegram-reminder`. Том `reminder-data` при этом сохраняется, уже отправленные слоты не пропадают. Не добавляйте флаг `-v`: он удалит историю слотов.

Если каталога ещё нет и контейнер когда-то создавали вручную:

```bash
sudo docker ps -a --filter name=telegram-reminder
sudo docker stop telegram-reminder
sudo docker rm telegram-reminder
```

После `docker compose down` имя `telegram-reminder` свободно, и новый запуск сможет его занять.

## 2. Настройка окружения

На сервере нужен каталог с файлами `docker-compose.yml`, `.env`, `message.json` и `users_map.json`. Репозиторий целиком клонировать не нужно.

```bash
sudo mkdir -p /opt/telegram-reminder
cd /opt/telegram-reminder
sudo nano .env
```

Вставьте свои значения. Пустые поля бот не примет и завершится с ошибкой ещё до расписания. Docker из-за `restart: unless-stopped` поднимет его снова, поэтому смотрите первую строку лога.

```env
BOT_TOKEN=123456:ABC...
CHAT_ID=-1001234567890
TZ=Asia/Bishkek
SEND_HOURS=19,20,21
JIRA_URL=https://your-company.atlassian.net
JIRA_USER=you@company.com
JIRA_API_TOKEN=ATATT...
JIRA_BOARD_PROJECT_KEY=PROJ
```

Сохраните файл: `Ctrl+O`, `Enter`, затем `Ctrl+X`.

### BOT_TOKEN

Токен бота из BotFather. Бот должен быть добавлен в рабочую группу и иметь право писать в неё. Это не пароль Jira и не токен API Atlassian.

### CHAT_ID

Числовой id группы, куда уходит сводка. У супергруппы он обычно начинается с `-100`. Одно сообщение слота всегда уходит в этот один чат.

### TZ

Часовой пояс группы, имя из базы IANA. Пример для UTC+6: `Asia/Bishkek`. От этого зависят и минута отправки, и граница суток для догона. `UTC+6` или `+06:00` бот не примет. Неизвестное имя завершает процесс с ошибкой.

### SEND_HOURS

Часы отправки через запятую, каждый от 0 до 23. Пример `19,20,21` значит три отдельных слота: в 19:00, 20:00 и 21:00 по `TZ`. На каждый час — одно сводное сообщение. Минута всегда 00. Поминутной проверки нет.

Если контейнер поднят в 20:30 и слоты 19 и 20 сегодня ещё не отправлены, он отправит их сразу, а слот 21 дождётся 21:00. Если его включили уже на следующий день, вчерашние 19:00, 20:00 и 21:00 не отправляются.

Пустое `SEND_HOURS` в работающем `.env` лучше не оставлять. В примере выше часы заданы явно.

### JIRA_URL

Адрес сайта Jira Cloud, только `https`, без слэша в конце и без логина в самой ссылке. Верно: `https://your-company.atlassian.net`. Неверно: `http://...`, `https://user:token@...` и адрес конкретной задачи `/browse/PROJ-1`. Бот сам ходит в `POST /rest/api/3/search/jql`.

### JIRA_USER

Почта учётной записи Atlassian, от имени которой бот читает задачи. У этой учётной записи должно быть право видеть проект. В Jira это обычный пользовательский API token, не OAuth-приложение.

### JIRA_API_TOKEN

API-токен Atlassian для `JIRA_USER` (Account settings → Security → Create and manage API tokens). Это не `BOT_TOKEN`. Токен в лог не пишется. Если Jira ответит ошибкой, в логе будет код HTTP, а не значение токена.

### JIRA_BOARD_PROJECT_KEY

Ключ проекта, как он выглядит в номере задачи до дефиса. Для `PROJ-12` ключ — `PROJ`. Бот подставляет его в запрос:

```text
project = PROJ AND status = "In Progress" ORDER BY created DESC
```

В сводку попадают только задачи этого проекта в статусе `In Progress`, новые сверху. Задачи в других статусах, в том числе To Do и Done, и задачи других проектов не входят. Если в вашем процессе этот статус называется иначе, например «В работе», запрос его не увидит: имя статуса в JQL именно `In Progress`.

Ключ должен начинаться с буквы и дальше содержать только буквы, цифры и `_`.

## 3. Конфигурационные файлы

Оба файла должны существовать как файлы до первого `docker compose up`. Если пути нет, Docker создаст на его месте каталог, и бот не сможет прочитать текст.

Русский текст в `nano` с клавиатуры сервера обычно не набирается. Напишите файл на своём компьютере, скопируйте и вставьте в `nano` правой кнопкой или `Ctrl+Shift+V`. Если вставка превращается в знаки вопроса, в `locale` строка `LANG` должна быть UTF-8, например `en_US.UTF-8`. После смены локали зайдите по SSH заново.

Файлы читаются заново в момент каждой отправки. Правка заголовка или карты действует на следующий слот без перезапуска контейнера.

### message.json

Это шаблон и заголовок напоминания. Текст из поля `text` всегда стоит в начале сообщения. Ниже бот дописывает задачи Jira.

```bash
sudo nano message.json
```

```json
{
  "text": "Сводка открытых задач"
}
```

Необязательное поле `parse_mode` со значением `HTML` или `Markdown` включает разметку Telegram для всего сообщения. Разметку пишите в `text` сами. Названия и имена из Jira при `HTML` бот экранирует, чтобы символы `<`, `>` и `&` не ломали сообщение. Пинг из карты остаётся как есть.

```json
{
  "text": "<b>Сводка открытых задач</b>",
  "parse_mode": "HTML"
}
```

Поле `text` должно быть непустой строкой. Иначе слот не считается отправленным.

### users_map.json

Карта «отображаемое имя в Jira» → «пинг в Telegram». Ключ — точное `displayName` исполнителя, как оно показано на карточке задачи. Значение — пинг, обычно `@username`.

```bash
sudo nano users_map.json
```

```json
{
  "Иван Иванов": "@ivan",
  "Мария Петрова": "@maria"
}
```

Имя копируйте из Jira целиком: те же буквы, пробелы и регистр. `Иван Иванов` и `Иван иванов` — разные ключи. У двух людей с одинаковым отображаемым именем пинг будет общий, потому что совпадение идёт по строке.

Если исполнителя нет в карте, строка задачи всё равно попадает в сводку: будет имя из Jira и не будет `@username`. Сообщение из-за этого не отменяется.

Если у задачи нет исполнителя, в строке будет «без исполнителя» и тоже без пинга.

Если файла нет, это не JSON или значения не строки, бот не отправит этот слот и не пометит его выполненным. Исправьте файл: следующая попытка в те же сутки прочитает его заново.

Так выглядит кусок сводки. `PROJ-2` нет в карте, поэтому у Марии нет пинга:

```text
Сводка открытых задач

PROJ-1: Починить отчёт
Исполнитель: Иван Иванов @ivan
https://your-company.atlassian.net/browse/PROJ-1

PROJ-2: Обновить инструкцию
Исполнитель: Мария Петрова
https://your-company.atlassian.net/browse/PROJ-2
```

Если задач в статусе In Progress нет, уходит заголовок и строка «Незакрытых задач нет.». Очень длинный список обрезается до одного сообщения Telegram и заканчивается пометкой, что показаны не все задачи.

## 4. docker-compose.yml

Откройте файл:

```bash
sudo nano docker-compose.yml
```

Вставьте текст целиком. Политика `restart: unless-stopped` поднимает контейнер после перезагрузки сервера и после падения процесса, если демон Docker включён в автозагрузку. `users_map.json` смонтирован только на чтение, рядом с `message.json`. История слотов лежит в томе `reminder-data`, а не в каталоге на хосте.

```yaml
services:
  reminder:
    image: ghcr.io/rdog49/reminder_telegram_bot:latest
    pull_policy: always
    container_name: telegram-reminder
    init: true
    restart: unless-stopped
    security_opt:
      - apparmor=unconfined
    env_file:
      - .env
    volumes:
      - ./message.json:/app/message.json:ro
      - ./users_map.json:/app/users_map.json:ro
      - reminder-data:/app/data

volumes:
  reminder-data:
```

`Ctrl+O`, `Enter`, `Ctrl+X`.

## 5. Деплой и запуск на сервере

Docker Engine и плагин Compose уже стоят, демон включён в автозагрузку:

```bash
sudo systemctl enable --now docker
```

В репозитории на ветке `main` должна быть зелёная сборка **Publish image**. Пока её нет, `docker compose pull` не найдёт образ. Если `pull` просит логин, пакет ещё приватный: GitHub → Packages у пользователя `rdog49` → Visibility: Public.

Из каталога с четырьмя файлами:

```bash
cd /opt/telegram-reminder
sudo docker compose pull
sudo docker compose up -d
```

`pull` скачивает образ. `up -d` создаёт контейнер в фоне и оставляет его работать. Процесс внутри не выходит после первой отправки.

Проверка:

```bash
sudo docker compose ps
sudo docker compose logs -f
```

В `ps` у сервиса состояние `running`. В логе при старте есть строка с часами расписания и часовым поясом, например `Расписание: 19,20,21, часовой пояс Asia/Bishkek`. Если текущий час уже из `SEND_HOURS` и слот сегодня не отправлен, следом будет попытка отправки. Выход из логов: `Ctrl+C`. Контейнер при этом продолжает работать.

Ошибка вроде «В .env нужны JIRA_USER и JIRA_API_TOKEN» или «JIRA_URL должен быть https-адресом» значит, что процесс остановился до расписания. Исправьте `.env` и пересоздайте контейнер:

```bash
sudo docker compose up -d --force-recreate
```

## Как уходит сообщение

В 19:00, 20:00 и 21:00 по `TZ` (или в те часы, которые записаны в `SEND_HOURS`) бот один раз собирает сводку и шлёт её в `CHAT_ID`. На один слот — одно сообщение.

Слот помечается отправленным только после успеха Telegram. Если Jira или Telegram недоступны, бот делает до трёх попыток с паузой 30 секунд и не записывает слот. Процесс при этом не завершается. Следующий час из `SEND_HOURS` в те же сутки снова попробует неотправленные более ранние часы. Отдельный поминутный опрос не запускается.

Перезапуск в те же сутки догоняет только сегодняшние наступившие часы, которых ещё нет в `reminder-data`. Вчерашние пропуски не отправляются.

## Обновление

Новый код попадает в реестр после зелёной сборки в `main`. На сервере:

```bash
cd /opt/telegram-reminder
sudo docker compose pull
sudo docker compose up -d
```

Текст `message.json` и карта `users_map.json` подхватываются при следующей отправке. Перезапуск для них не нужен.

После правки `.env` контейнер нужно пересоздать:

```bash
sudo docker compose up -d --force-recreate
```

## Остановка

Остановить контейнер и оставить историю слотов:

```bash
cd /opt/telegram-reminder
sudo docker compose down
```

Том `reminder-data` сохраняется. Следующий `sudo docker compose up -d` продолжит с теми же слотами.

Откат на старый образ возвращает программу, которая завершается после одной попытки. Вместе с `restart: unless-stopped` контейнер начнёт сразу перезапускаться, а текст снова будет только из `message.json`. Том со слотами при откате удалять не нужно. Расписание по-прежнему не выносится в системный cron.
